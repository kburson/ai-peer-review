## Pair decision

The initial decision below is retained as the evidence chronology; the renewed Claude decision later in this record supersedes it.

The Grok author / Codex reviewer XPR is a candidate for further investigation, **not a qualified automatic pair**. The bounded live experiment in this worktree started Grok Build `1.0.34` and Codex CLI `0.155.0-alpha.9.2` in distinct exact sessions. Grok launched a GPT-5.5 reviewer through the installed Codex CLI, read its first answer, and invoked `codex exec resume` with the returned exact session ID. Both Codex JSONL runs reported `turn.completed` for the same ID. Grok's own saved assistant messages carry per-message model ID, model fingerprint, and effort. Codex's saved `turn_context` records carry model and effort for each turn; its user prompt, assistant reply, and `task_complete` event are ordered within the same exact session and turn. The [official Grok headless guide](https://docs.x.ai/build/cli/headless-scripting) and [official Codex non-interactive guide](https://developers.openai.com/fr-FR/docs/non-interactive-mode) document exact session resume. A separate retained Grok headless peer-review session has five `turn_started` records (0–4) with one session ID and four completed outcomes after an initial cancellation, showing that the installed Grok surface can also accept repeated exact-session turns.

These first-party product records suggest a possible reconciliation mechanism: a unique operation marker in a delivered prompt could be matched to a persisted exact-session user turn and terminal outcome. The experiment did not test that marker or recovery after a lost receipt. An incomplete or absent provider record must remain `outcome-unknown` unless non-submission was proven before dispatch, with no blind retry. The persisted JSONL schemas are first-party local records rather than documented stable public APIs, and neither surface has a production adapter that validates them. They therefore do not yet satisfy Task 1's official exact-session evidence and reconciliation gate. No Claude pairing is claimed from this experiment. Gemini/Antigravity remains excluded from the production selector set.

## Renewed Claude conformance and Task 1 decision

After the operator confirmed that Claude's subscription window had reset and authorized another test, one bounded installed CLI exercise used Claude Code `2.1.278` without API-key environment variables. It made two fresh `claude-opus-5` sessions at requested `medium` effort and one exact `--resume` of the first session. All three calls exited zero and emitted a success result. The two fresh session IDs differed; the resumed result and provider transcript retained the first ID. Each provider-owned transcript recorded an assistant turn with `message.model: claude-opus-5`, `effort: medium`, and `message.stop_reason: end_turn`. Each streamed system initialization identified the model and exact session. Each rate-limit event reported `allowed` and no overage. Raw IDs, prompts, and transcripts remain only in ignored local provider/scratch storage.

The resumed prompt carried a unique operation marker. Reading only the provider-owned session transcript after the CLI call found exactly one matching user prompt followed by a terminal assistant turn in that same session with the observed model and effort. This is a read-side demonstration of how a lost local receipt can be reconciled: a matching terminal turn is acknowledged; an absent or incomplete turn remains unknown and is never blindly retried. The exercise did not kill a provider process mid-turn or implement the production broker's crash path. The [official headless guide](https://code.claude.com/docs/en/headless) documents exact session resume and streamed results; the [official session-directory guide](https://code.claude.com/docs/en/claude-directory) identifies the provider-owned session transcript; the [official hooks guide](https://code.claude.com/docs/en/hooks) documents effective `effort.level`. The installed transcript itself supplies the per-turn model, effort, session, and terminal outcome. Its schema must be pinned to the installed version and rejected on drift.

The first exercise alone did not prove a model observation during an in-progress reviewer join: the [official hook input contract](https://code.claude.com/docs/en/hooks) warns that the transcript may lag, and `PreToolUse` has no model field. A second bounded installed exercise used a temporary owner-only hook and real-time `stream-json` with `--verbose`. The hook's `SessionStart` input omitted optional `model`, so that route is unavailable on this run. The provider stream instead emitted `system/init` with the exact session and `claude-opus-5`, then an `assistant` tool-use message with the same session and model before the Bash operation. `PreToolUse` for that operation carried the same exact session ID and a prompt ID. The call completed successfully with rate-limit status `allowed`; no separate API key was present. The official [headless guide](https://code.claude.com/docs/en/headless) documents that `stream-json` is real-time and that `system/init` reports model and session metadata. This is an observable source for the in-progress join: the package-owned launch stream can persist the model/session observation before the reviewer tool call enters `peer-review join`, while the hook confirms the tool belongs to that session. Missing events, changed model/session, stale evidence, or an incomplete operation must fail closed.

**Task 1 pair result:** Claude author / Claude reviewer SPR qualifies at the installed-surface level under the operator-amended gate. Two fresh sessions were distinct; exact resume and completed-turn provider records support wake and outcome reconciliation; the streaming/tool-use exercise supplies active model and session before an in-progress join. This is capability evidence, not a claim that the current package adapter or installed broker performs the binding, streaming, or crash recovery. Codex/Grok XPR remains unqualified. Gemini/Antigravity remains outside the production selector set.

## Policy consequence

The package evaluator now requires official exact-session model and session evidence; exact delivery and reconciliation; a version match; and fresh health. Reviewer launch additionally requires exact launch. The selected effort is retained as requested configuration but is not represented as provider-observed fact. Production adapters lacking the required proof expose only manual or recovery capability. A deterministic fully evidenced test fixture exercises the evaluator's positive branch without becoming a production conformance row.
