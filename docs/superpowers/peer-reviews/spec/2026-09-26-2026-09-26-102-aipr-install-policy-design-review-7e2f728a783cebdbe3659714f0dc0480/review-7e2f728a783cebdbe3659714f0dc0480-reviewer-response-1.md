## Summary

I reviewed `docs/superpowers/specs/2026-09-26-102-aipr-install-policy-design.md` against the current implementation in this worktree (`src/config/load.mjs`, `schemas/config-v1.json`, `src/doctor.mjs`, `src/cli/parse.mjs`, `src/cli/run.mjs`, `src/git/repository.mjs`, `src/public-api.mjs`).

The design is coherent and unusually disciplined about the hard parts. The choices I checked most closely all hold up: exact-equality pinning with no bypass knob, executing-package metadata as the only identity source, effect-based operation classification with unclassified operations denied by default, revalidation after asynchronous waits, and the narrow cleanup exception that still requires proven ownership. I verified the read-only classification claim against the code rather than accepting it: `resumeReview` (`src/cli/run.mjs:1705`) delegates to `statusReview` and only formats instruction text, so listing `resume` as read-only is accurate; `joinReview` calls `mutateReview` and `createResponseDraft`, so listing `join` as gated is likewise accurate.

Five issues need resolution before this design is implementable as written. Four are concrete conflicts with the existing code or with the design's own stated goals; one is an unstated operational deadlock. Two are specification gaps that different implementers would resolve differently, which is exactly what this document exists to prevent.

The most important is F1: the user-level `tool` prohibition has no defined enforcement point, and the current merge semantics actively defeat the obvious implementation. The most operationally consequential is F2: making `unconfigured` a doctor failure, combined with prescribing doctor as the CI gate, converts an explicitly opt-in feature into a forced migration for every existing consumer on the upgrade that ships it.

## Findings

1. **A user-level `tool` can supply a project pin under current merge semantics, and the design never says where the prohibition is enforced.** §Authority And Root Resolution states "A user-level `tool` is invalid and cannot supply, override, or complete a project pin," but specifies no observable outcome — no error code, no exit status, no acceptance assertion. The code makes this a live defect rather than a wording nit. `loadConfig` (`src/config/load.mjs:320`) computes `merge(user, project)` and then validates the merged object; `merge` (`src/config/load.mjs:284`) deep-merges with the right operand winning. Once `tool` is added to `TOP_LEVEL` (`src/config/load.mjs:12`) so that project configs validate, a `tool` object in the user file becomes schema-valid in isolation, survives the merge whenever the project file omits `tool`, and is indistinguishable from a project pin in `loaded.config`. Worse, because the merge is recursive, a user file supplying `{"tool":{"package":"@kburson/ai-peer-review"}}` and a project file supplying only `{"tool":{"required_version":"0.4.0"}}` deep-merge into a complete, valid pin — precisely the "complete" case the sentence forbids. An implementer following the schema-first instruction in §Configuration Contract ("Update `schemas/config-v1.json` and the independent validator in `src/config/load.mjs` together") lands on exactly this broken shape, because both artifacts today are source-agnostic. The design must name the enforcement point and the outcome. The natural one already exists: `readConfig` (`src/config/load.mjs:274`) validates each file individually before merging, so `validateConfig` needs a source discriminator (user vs. project) and must raise `APR_CONFIG_INVALID` on a `tool` key read from the user path. That is a signature change to an exported validator and therefore a public API change under the document's own rule in §Evaluation And Entry Points, which currently goes unmentioned. AC5's "User config cannot supply policy" is too weak to pin this down; it must assert the specific code, the nonzero exit, the partial-`tool` deep-merge case, and that policy evaluation reads raw project bytes rather than `loadConfig` output.

2. **Doctor failing on `unconfigured` plus doctor-as-CI-gate makes an explicitly opt-in feature mandatory on the upgrade that ships it.** §Diagnostics And Recovery states "Doctor is unhealthy and exits nonzero for ... unconfigured policy," and §Worktrees, CI, And Rollout states CI "runs doctor before review work." §Legacy State says "Protection is opt-in for existing projects." These cannot all hold. `src/doctor.mjs:98` computes `healthy` as an all-or-nothing conjunction over rows marked required, so a required `tool-policy` row that reports `unconfigured` as unhealthy turns doctor red — and any CI job gating on it red — for every existing project the moment the operator upgrades a global installation, before that project has had any opportunity to adopt a pin. This is the one place where the design's otherwise careful separation between "warn" and "refuse" collapses: legacy mutations stay permitted, but the prescribed health gate blocks the pipeline that would run them. The Resolved Decisions entry ("doctor reports lack of protection as unhealthy") records the intent but not this consequence. Either the `tool-policy` row is non-required by default with an explicit opt-in strictness flag for projects that want CI to demand adoption, or the design must state plainly that this is a breaking change to doctor's exit status, name the release that carries it, and describe the migration window. My recommendation is the former: it preserves the stated opt-in property, and projects wanting enforcement can turn it on deliberately, which matches how every other gate in this design works.

3. **Root-resolved policy alongside cwd-resolved configuration creates two project configs and a bypass surface.** §Authority And Root Resolution requires reading policy "from the raw project `.ai-peer-review.json` at the physical worktree root." But `configPaths` (`src/config/load.mjs:303`) currently derives the project config as `path.join(path.resolve(cwd), '.ai-peer-review.json')`, so a subdirectory invocation today loads *no* project config at all and silently runs on user-level settings. The design says "Subdirectory invocation uses that root" for policy, and says nothing about the rest of the configuration. As written it permits an implementation where policy comes from the worktree root while `authority`, `hosts`, and `review` come from whatever `.ai-peer-review.json` happens to sit in the caller's cwd — two different files, one command. A nested config in a subdirectory could then supply authority or host settings that the root-level, tracked, reviewed config never contained, while the pin check passes cleanly against the root. This undercuts the goal in §Problem And Goals of preserving "provider identity, authority, and integrity checks." State explicitly whether `configPaths`/`loadConfig` move wholesale to worktree-root resolution — which I believe is the correct answer and is itself a behavior change worth calling out, since it changes what subdirectory invocations load today — or, if only policy is root-resolved, state that a non-root `.ai-peer-review.json` is an error rather than a silent second source. AC5's "subdirectory invocations agree" needs to be sharpened to assert which file supplied each section.

4. **Mismatch-gated `setup --remove` creates an uninstall deadlock with no documented escape.** The operations table gates "Project setup, including `--remove`" on configured compatibility, and §Ordinary Setup confirms removal "never adopts policy." So a project pinned to a version the operator can no longer install — a yanked release, a development build, an unavailable platform binary — cannot have its integration material removed by the tool that installed it. The document does establish the escape in principle: §Problem And Goals lists "Preventing a repository owner from editing or removing policy" as a non-goal, so hand-deleting the `tool` object is intended to work. But that connection is never made on the removal path, where an operator will actually hit it, and the refusal's recovery text is the only place it would help. Either grant `--remove` a narrowly scoped exception on the same footing as the cleanup exception — it removes only owned integration material, cannot admit review work, and already preserves the pin — or state explicitly that the documented recovery for a mismatch on `--remove` is to delete the `tool` object first, and require that the `APR_TOOL_VERSION_MISMATCH` recovery guidance for this command say so. AC8 must cover removal under mismatch either way; today it covers only that "removal never adopts one and preserves existing policy and foreign content," which passes trivially if removal is simply always refused.

5. **The lock location is specified by a raw Git invocation that bypasses the abstraction the document mandates elsewhere, and its "not in the common Git directory" claim is imprecise.** §Activity Preconditions requires resolving the lock directory with `git rev-parse --absolute-git-dir`, while §Authority And Root Resolution requires resolving the worktree "through the existing Git abstraction." `src/git/repository.mjs` already resolves administrative paths (`rev-parse --git-path`, `src/git/repository.mjs:194`) and the common directory (`--git-common-dir`, `src/git/repository.mjs:143`), so the new raw call adds a second, unabstracted Git surface subject to none of that module's argument and output handling — and §Diagnostics And Recovery separately requires that read-only Git invocations disable optional index refresh writes, a constraint the abstraction is the right place to enforce. The descriptive claim also needs correcting: in a linked worktree the administrative directory is `<common>/worktrees/<name>`, which is physically *inside* the common Git directory even though it is per-worktree, and in an ordinary clone the administrative directory *is* the common directory. The isolation property the design wants is real, but the stated justification is wrong as written and will mislead whoever implements the stale-lock and per-worktree-isolation tests in AC9. Give the exact resolved path template for both cases, route resolution through `src/git/repository.mjs`, and note that the reclamation receipt (§Coordination Lock Recovery) lands in the same directory as the lock it protects, so the design should say what happens when that directory is unwritable — currently the "failed retention leaves the lock or retained evidence discoverable and refuses new work" rule assumes writability it never establishes.

## Optional suggestions

1. **Build metadata in `required_version` is unreliable as a distributed identity.** §Configuration Contract admits build identifiers (`1.2.3-rc.1+build.07`) and requires exact string equality including the build suffix. For a locally built or linked package this works, because the version string in `package.json` is whatever was written there. For anything that round-trips through the npm registry it is fragile: build metadata is not part of a release's identity for resolution purposes, and relying on it to distinguish two published artifacts is unsound. §Runner Identity And Selection already makes the right point — "Released fixes need distinct versions" — so I suggest saying directly that build metadata is supported for local and development builds only and must not be used to distinguish published releases. Worth a sentence; I am flagging the direction rather than asserting exact registry normalization behavior, which the implementation plan should confirm.
2. **Relate the new `tool-policy` row to the existing `package` row.** `src/doctor.mjs:21` already emits a required `package` row driven by `context.packageResolved`. Two adjacent rows named `package` and `tool-policy`, both concerning package identity but answering different questions, will read ambiguously in both text and JSON output. A clause stating what each covers — and that `tool-policy` reports independently even when `package` is unavailable, which §Diagnostics And Recovery already implies — would prevent the confusion.
3. **Ordinary `setup --dry-run` exit codes change.** §Diagnostics And Recovery makes previews exit nonzero when application would be blocked. `--dry-run` already exists for `setup` (`src/cli/parse.mjs:12`), so this alters the exit status of a shipped flag for reasons unrelated to policy adoption. AC15's golden-output fixtures will catch it, but the compatibility note belongs in §Worktrees, CI, And Rollout alongside the other rollout consequences rather than being discovered as a test failure.
4. **The idempotent no-op path skips an unstated check.** §Setup And Adoption states that when target and expected pin already equal the current runner, policy-only setup is "an idempotent no-op after validation: no write, lock, or idle precondition is needed." It does not say whether the tracked-stage-zero requirement is still evaluated on that path. A pin that is present, matching, and untracked should presumably still surface `APR_TOOL_POLICY_UNTRACKED` rather than exiting zero, since the operator's next mutating command will refuse. Stating which checks survive the no-op shortcut would remove the ambiguity; AC9's "no-op updates are idempotent" does not currently distinguish the two readings.
