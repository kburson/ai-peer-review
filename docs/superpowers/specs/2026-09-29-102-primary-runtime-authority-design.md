# Primary-Workspace AIPR Runtime Authority Design

## Status and provenance

- Issue: [#102](https://github.com/kburson/ai-peer-review/issues/102).
- Status: draft replacement for `2026-09-26-102-aipr-install-policy-design.md`. The earlier accepted XPR remains historical evidence for its earlier requirements; it does not approve this design.
- User decision: one primary-checkout AIPR config per repository clone, project-local dependencies in each checkout, one current global AIPR installation on the planning host, and **no exact project package-version pin**. A globally replaced version is not treated as available through a worktree-local package or retained runtime image.
- Planning boundary: revise #102's issue scope and acceptance criteria only after this design is accepted. The superseded implementation-plan draft must not be executed. #107's per-run older-installation routing proposal must also be reconciled before it is implemented.

## Problem and outcome

The earlier #102 design made each physical worktree's `.ai-peer-review.json` an independent exact package-version authority. That would require repeated config changes when one global installation changes, and it implies that an older worktree-local installation could still be selected. Neither behavior matches the intended operating model.

For one Git repository clone, the primary checkout owns the project AIPR configuration. Linked worktrees use that config while retaining their own project-local `node_modules` for their own dependencies. AIPR review mutations use the currently registered global AIPR package on the planning host. The active review worktree remains the authority for its Git state, review files, provider sessions, and broker ownership. An upgrade never silently replays an old review with a stored older executable.

Success means a global update requires no version-pin edit in each project or worktree. The updated runtime either proves it supports an existing review's recorded format and operation or refuses mutation with intact evidence. Stale copied integrations and divergent source checkouts cannot bypass that check.

## Authority domains

| Domain                   | Authority                                                                                  | Boundary                                                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository identity      | Validated Git common directory                                                             | Groups primary and linked worktrees of one clone only.                                                                                                         |
| Primary checkout         | Clone-local primary registration under the common Git administrative directory             | Stores a canonical path and Git identity; no inference from current directory name or a sibling config.                                                        |
| Project config           | Primary checkout's `.ai-peer-review.json`                                                  | All config sections (`authority`, `hosts`, `review`, `setup`) come from this one file. No `tool.required_version` or other exact package pin.                  |
| Selected AIPR runner     | Clone-local registration of a canonical, installed global package path and Node executable | Registration records paths and installation identity, not a required version. Every invocation checks that its executing module is that selected installation. |
| Review and Git state     | Physical worktree in which the review was started                                          | Review artifacts, runtime observations, Git snapshots, scratch, and broker ownership do not move to the primary checkout.                                      |
| Historical runtime image | Immutable review evidence                                                                  | An image with older package bytes is never an alternate executable after a global update.                                                                      |

The clone-local registration is machine state, not a tracked project file. Put it under the validated Git common administrative directory with owner-only permissions, an explicit schema, atomic writes, and an installation/primary-path change receipt. The tracked primary config remains portable across machines. A bare repository, absent primary checkout, moved primary checkout, missing registration, unreadable registration, foreign worktree, or ambiguous ownership fails closed for project mutation. `help` and `explain` remain available without Git. User-scoped setup outside Git remains available without consulting a project config.

The registration command accepts a primary checkout only when it is the validated main worktree of that common directory. It records the real path and Git common-directory identity, then reads it back before reporting success. It never adopts a linked worktree merely because a caller labels it primary. Registration of a replacement primary requires an explicit operator action, a dry-run diff, and a read-only inventory of active reviews; it does not move or rewrite review evidence. A primary path that no longer validates remains unavailable until repaired explicitly.

## Configuration and setup

`configPaths` and `loadConfig` resolve the caller's physical worktree, validate its Git common directory, locate the registered primary checkout, and read the primary `.ai-peer-review.json`. Subdirectory and linked-worktree invocations therefore use the same project file. A same-named file in a linked worktree is ignored as project authority and diagnosed if it conflicts. It is not merged. User config retains its existing per-user path and merge precedence for unrelated settings; project setup ownership and every project config section come from the primary file. An explicit workspace or invitation path must still agree with the caller's validated physical worktree; a shared config cannot authorize cross-worktree review mutation.

The public `configPaths` result includes `project` as the primary file path, `primaryRoot`, and `activeWorktreeRoot`. Outside Git, `project` and both roots are `null`; user setup reads only user config, while project mutation refuses missing identity. This is a documented public API change. The loader rejects invalid, unreadable, or symlinked primary config rather than treating it as absent. The primary config may be absent for a new clone; initial project setup creates it through the normal ownership rules. A conflicting linked-worktree config is diagnostic data only and cannot complete a missing primary field.

Project `setup`, `setup --update`, and `setup --remove` target only the primary checkout's owned config and host integration files. A linked-worktree invocation resolves that target and reports it before apply. User-scope setup remains separate. Existing foreign-file and ownership protections remain. No setup operation writes an exact AIPR package version requirement. The legacy `setup.package_version` field can be read for migration but is no longer a gate requiring the current global version to equal old copied setup metadata; its presence must not silently bless a stale copied skill or hook.

Package-owned host integrations must invoke the registered global CLI/hook entry points. Where a host requires project-local discovery, a linked worktree uses a verified pointer to the primary integration, or a supported user-scope integration; it must not run a stale tracked copy as current package code. The implementation plan must choose the host-specific mechanism from observed Codex/Claude behavior and test it on supported platforms. A foreign or conflicting tracked integration is reported and preserved, not replaced on `doctor`. A global AIPR upgrade may require one primary or user-scope integration refresh if the integration contract changed; it must never imply one refresh per linked worktree. Read-only doctor reports this separately from runtime compatibility.

## Project-local dependencies and CI boundary

Each project checkout and linked worktree retains its own `node_modules` for that project's dependencies and branch-specific development needs. AIPR setup, doctor, and review commands never link, replace, delete, or install those dependencies. The project-local tree is not an AIPR runtime selector. If an older `@kburson/ai-peer-review` happens to be present there, it is not used for governed review mutations; a source checkout can still run its own code for package development tests under an explicit test harness. Production review mutations from that source or local installation refuse unless it is the registered current global installation. There is no caller-supplied bypass flag.

AIPR is a planning-time tool on the developer or agent host. Consumer projects' cloud CI and runtime builds do not need a global AIPR installation, clone-local registration, `peer-review doctor`, or a review gate. Merely checking out a repository with `.ai-peer-review.json` cannot make its normal tests or deployment depend on AIPR. If a CI job explicitly invokes an AIPR command, that job has intentionally opted into provisioning and checking the tool. AIPR's own package CI remains responsible for unit, integration, packaging, and installed-artifact compatibility tests; those tests use isolated fixtures rather than modifying the machine's real global npm installation.

## Current runtime and review compatibility

The registered global installation is selected by canonical package root and Node executable, not by `PATH`, cwd, an environment variable, a local dependency, or a caller-provided version string. At each entry point, derive name/version and supported authority, review, runtime-image, broker-protocol, hook, and MCP formats from the package containing the executing module. Compare the real executing path with the registration. An in-place global upgrade retains the path but changes observed package metadata and installed-file digest; no config version edit is required. A relocated global installation needs explicit re-registration. Seal the executing process's package-file digest at startup and compare the on-disk global installation before later effects. If npm replaces files while an old process remains alive, that process fences further mutation; a fresh invocation loads and checks the new code. Invalid package metadata, incomplete installation, or a changed/unsafe path refuses mutation.

At review start, seal the current package version, installation identity, format versions, and worktree identity in the run authority. These are provenance and compatibility inputs, not a request to keep an old executable. Before each state-changing operation, inspect the recorded formats and the current package's declared supported-format matrix. A match admits the operation only after existing identity, provider, Git, ownership, and protocol gates pass. An unknown or unsupported format returns `APR_REVIEW_RUNTIME_UNSUPPORTED` with the observed package, recorded format identifiers, review path, and safe guidance. Version equality alone neither proves compatibility nor grants authority. If an older format becomes supported by a later package, that support must be explicit and covered by installed-artifact tests; no automatic journal rewrite is implied.

Existing runtime images remain immutable evidence and can be validated for integrity, but an image may execute only when its verified package-file digest and Node identity equal the **currently selected global installation** for the same run and operation. Version-string equality alone is insufficient. An older image is not a fallback after upgrade, even if its files or a worktree-local AIPR package still exist. Broker startup, worker restoration, offline reconciliation, MCP, hooks, and exported state writers independently enforce the current-installation and supported-format checks before effects. A mismatched older image cannot be launched to make `status`, `doctor`, or cleanup appear successful.

If the global package changes while work is in progress, the next effect boundary revalidates the current installation and format support. A supported new runtime may continue under the same review authority; an unsupported one fences new work, preserves all existing evidence, and provides read-only status. Owned stop/suspend/cancellation is permitted only when the current runtime can prove the existing broker's protocol, root, and ownership; otherwise it reports that safe cleanup is unavailable. It never launches an older image or kills a process by PID guess. No package can guarantee an operator will not replace a global npm installation mid-operation; the guarantee is fail-closed admission and revalidation at subsequent mutation boundaries.

## Diagnostics and rollout

Doctor shows independent rows for primary registration/config, selected global package, copied integration compatibility, current review format support when a review is named, provider identity, and broker health. `doctor --mode installation` does not require a current provider/model. It reports physical paths and bounded reasons without dumping environment/config or executing candidate packages. Help and explain work without Git. Status and other read-only inspection keep their successful stdout schemas and report unsupported runtime separately on stderr or structured diagnostic fields already allowed by their schema. Diagnosis never installs, fetches, rewrites a review, or starts a broker.

Rollout first registers the primary checkout and current global installation for each local clone, validates the primary config, then refreshes primary/user integrations. Each linked worktree resolves that same config before review mutation; its project dependencies remain local. Existing review state is inventoried before a global update where possible; an operator can finish or settle incompatible reviews before upgrading. After an uncoordinated upgrade, unsupported reviews stay fenced rather than silently using a retained old package. Primary setup preserves foreign and unrelated edits. The old exact-pin spec, proposed `--pin-tool-version` modes, policy locks, and per-worktree pin tests are not implemented.

The #107 proposal currently assigns same-worktree legacy routing to older pinned installations. That ownership is incompatible with this decision. #107 must instead specify what the current installation supports and how unsupported legacy reviews remain inspectable/fenced; it may not route to an older package merely because an image or local dependency remains. #115/#117 recovery fixes remain valid for reviews whose selected runtime and formats are supported; their older-image fallback paths require an explicit compatibility audit before this design ships.

## Acceptance criteria for the replacement #102 scope

1. A validated primary registration resolves one project config for primary, linked, and subdirectory invocations; missing/moved/foreign/ambiguous primary state refuses project mutation. Worktree-local config cannot override or deep-merge it.
2. Existing user config and user setup work outside Git; project setup and all project config sections use the primary checkout and preserve owned/foreign boundaries.
3. Each primary or linked worktree may keep its own project-local `node_modules`; AIPR never rewrites, links, deletes, or treats that directory as runtime authority. Consumer CI and runtime builds do not require AIPR installation or a review/doctor gate.
4. The selected global package is identified by its executing module and registered canonical path; cwd, PATH, env, source checkout, local dependency, and API inputs cannot impersonate it. Global in-place upgrades do not require exact project version edits.
5. The current package's explicit format support, sealed review provenance, and existing authority checks govern review mutations. Unsupported/unknown old formats and invalid metadata fail before effects; supported formats continue only with existing integrity checks.
6. Older runtime images and worktree-local packages remain evidence or development artifacts and are never executed as an upgrade fallback. Broker, hooks, MCP, and exported writers enforce the same rule, including after async waits.
7. Unsupported review cleanup is bounded to proven current-runtime ownership and protocol; otherwise evidence remains and the operation refuses without guessing or launching older code.
8. Doctor distinguishes registration, config, selected package, integration, format support, identity, and broker health; read-only commands preserve successful output schemas and have no effects.
9. Setup migration is explicit and idempotent, changes primary/user integrations once per clone or user, and preserves foreign files and active review evidence. A source/local runner cannot bypass global selection.
10. Installed-package fixtures cover global upgrade, changed Node/global path, active and terminal older reviews, ordinary/linked/custom Git layouts, paths with spaces, and Windows and POSIX without real global-install or registry mutation. Consumer-project CI fixtures pass without AIPR installed.

## Open implementation sequencing, not design authority

Plan work in independently verifiable slices: primary registration/config; global runner selection and integration migration; review-format support and old-image fence; cross-entry-point enforcement; installed-artifact matrix. The implementation plan must map each criterion to tests and preserve the existing #102 review trail. No implementation begins from the superseded exact-pin plan.
