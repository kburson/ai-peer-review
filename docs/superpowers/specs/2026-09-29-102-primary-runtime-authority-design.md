## Problem and outcome

The earlier #102 design made each physical worktree's legacy `.ai-peer-review.json` an independent exact package-version authority. That would require repeated config changes when one global installation changes, and it implies that an older worktree-local installation could still be selected. Neither behavior matches the intended operating model.

For one Git repository clone, the primary checkout owns the project AIPR configuration and shared skill instructions. Linked worktrees use that config while retaining their own project-local `node_modules` for their own dependencies. AIPR review mutations use the currently registered global AIPR package on the planning host. The active review worktree remains the authority for its Git state, review files, provider sessions, and broker ownership. An upgrade never silently replays an old review with a stored older executable.

Success means a global update requires no version-pin edit in each project or worktree. The updated runtime either proves it supports an existing review's recorded format and operation or refuses mutation with intact evidence. Stale copied integrations and divergent source checkouts cannot bypass that check.

## Authority domains

| Domain                   | Authority                                                                                              | Boundary                                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository identity      | Validated Git common directory                                                                         | Groups primary and linked worktrees of one clone only.                                                                                                                                   |
| Primary checkout         | Clone-local primary registration under the common Git administrative directory                         | Stores a canonical path and Git identity; no inference from current directory name or a sibling config.                                                                                  |
| Project config           | Primary checkout's `.ai-peer-review/config.json`                                                       | All project policy sections come from this file; separately classified host preference fields come from untracked user bindings. No `tool.required_version` or other exact package pin.  |
| Selected AIPR runner     | One user/machine-scope registration of the canonical installed global package path and Node executable | Every clone uses the same selection record. Registration records locator identity, not a required version or file digest; each invocation observes and verifies current installed bytes. |
| Review and Git state     | Physical worktree in which the review was started                                                      | Review artifacts, runtime observations, Git snapshots, scratch, and broker ownership do not move to the primary checkout.                                                                |
| Historical runtime image | Immutable review evidence                                                                              | An image with older package bytes is never an alternate executable after a global update.                                                                                                |

The primary registration is clone-local machine state, not a tracked project file; global runner selection is a separate user/machine-scope record shared by all clones. Put the primary record under the validated Git common administrative directory with owner-only permissions, an explicit schema, atomic writes, and a primary-path/policy-activation change receipt. The separate user-scope selection record has its own installation-location receipt. The tracked primary config remains portable across machines. A bare repository, absent primary checkout, moved primary checkout, missing registration, unreadable registration, foreign worktree, or ambiguous ownership fails closed for project mutation. `help` and `explain` remain available without Git. User-scoped setup outside Git remains available without consulting a project config.

The registration command accepts a primary checkout only when it is the validated main worktree of that common directory. It records the real path and Git common-directory identity, then reads it back before reporting success. It never adopts a linked worktree merely because a caller labels it primary. Registration of a replacement primary requires an explicit operator action, a dry-run diff, and a read-only inventory of active reviews; it does not move or rewrite review evidence. A primary path that no longer validates remains unavailable until repaired explicitly. If a future package cannot read the prior machine-local registration schema, its registration repair path must inspect and preserve the old record, then write a current-schema replacement only through that explicit action; normal review commands cannot treat an unknown registration as valid.

## Primary file activation and branch changes

The registered primary working tree is the project authority, subject to an explicit activation receipt. Registration records `primary_initialized`, the activated config path/blob digest, the activated shared skill path/blob digest, and the integration contract identifier under the Git common directory. These are policy-content references, not an AIPR package-version pin. Once initialized, an absent config or skill is unavailable authority, never a new-clone default. An initial unconfigured registration is explicit and may be initialized only by setup from the primary checkout.

Before project mutation, require the primary Git identity to validate, the activated owned files to be ordinary non-symlink files with validated schemas, and their working-tree and index bytes to equal the activated committed blobs. Refuse if those owned files are staged, dirty, unmerged, or absent, or when a primary merge/rebase has unresolved, staged, or changed owned paths. An unrelated merge/rebase with identical clean owned blobs is a doctor diagnostic and does not by itself block linked review work. Unrelated primary edits do not invalidate clean owned files. A branch switch is permitted when the activated owned blobs remain identical; a pre-migration or different-policy branch refuses instead of silently replacing the authority. The receipt is revalidated at each effect boundary so a branch change during a review cannot silently change its policy. Read-only inspection reports the mismatch without activating anything. A pulled or committed policy change is diagnosed with old/new owned blob digests and the exact primary-only activation command, plus the active-review inventory prerequisite; neither pull nor doctor activates it implicitly.

A primary policy change is proposed through primary-only setup/migration or an ordinary reviewed policy edit. A dry run shows current branch, owned dirty paths, old/new paths and digests, and active review inventory. Setup refuses pre-existing staged or dirty owned files and never changes the index; after its atomic write, governed review mutation remains unavailable until the operator commits the owned changes and explicitly activates the new committed blobs. Activation records a before/after receipt, verifies read-back, and requires an idle inventory or a proven owned suspension for affected nonterminal reviews; it does not rewrite their sealed policy or evidence. Tests use isolated repository fixtures to exercise linked-branch policy or skill changes before merge. A linked branch's experimental policy is not a production authority and there is no production bypass flag for selecting it.

## Configuration and setup

`configPaths` and `loadConfig` resolve the caller's physical worktree, validate its Git common directory, locate the registered primary checkout, and read the primary `.ai-peer-review/config.json`. Subdirectory and linked-worktree invocations therefore use the same project file. A same-named file in a linked worktree is ignored as project authority and diagnosed if it conflicts. It is not merged. For project operations, `authority`, `review`, project `setup` ownership, and explicitly classified host policy fields come exclusively from the activated primary config. User values do not override or fill missing project policy. Omitted policy fields use documented package defaults or refuse when required. Host identity hints and executable bindings are explicitly classified user/machine preferences and resolved field-by-field from one untracked user source; there is no general deep merge. Outside Git, user-scoped setup uses the user config only and cannot activate project policy. Machine-specific runner selection and installation receipts live in their separate untracked authority stores. This intentionally replaces the current unconstrained user-to-project deep merge. An explicit workspace or invitation path must still agree with the caller's validated physical worktree; a shared config cannot authorize cross-worktree review mutation.

### Field ownership and host preferences

The new closed config schema separates portable project policy from untracked host bindings. Project `authority` and `review` fields remain primary-exclusive. Project `setup` contains only portable ownership, format and generated-content metadata; machine install paths and observations move to untracked receipts. For the existing `hosts.<host>` fields, use this complete classification:

| Field                                                                                  | Source during project operation                                                                   | Precedence and change behavior                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `identity` (provider, host, model ID/display)                                          | User preference hints, then official host/session observation                                     | Never a source of participant identity proof. Explicit run selection wins over a user hint; runtime/session evidence owns observations. No tracked machine/model identity; no primary activation for a preference/model change.            |
| `resume.command`                                                                       | User-exclusive machine binding validated by the provider adapter                                  | No primary override or fill-in. If absent, use a proven official adapter default or report unavailable. Seal the resolved command contract at run start; changing preferences does not rewrite existing reviews.                           |
| `reviewer_guard.enabled`                                                               | Primary project policy                                                                            | User config cannot disable a required guard. Missing uses the documented policy default. Policy changes require activation.                                                                                                                |
| `reviewer_guard.command`                                                               | User-exclusive machine binding constrained to the supported selected-global guard entry point     | A user path cannot substitute a foreign/source/local AIPR runner or weaken the enabled policy. Missing adapter capability refuses the required guard.                                                                                      |
| `automatic.adapter_version` and `automatic.capability`                                 | Primary project policy                                                                            | Defines allowed protocol/capability, not a machine executable. User bindings cannot widen capabilities.                                                                                                                                    |
| `automatic.server_command`, `tool_timeout_ms`, `heartbeat_interval_ms`, `lease_ttl_ms` | User-exclusive machine bindings validated against the project capability and protocol constraints | No primary executable paths. Enforce positive durations, lease greater than heartbeat, required timeout/capability readiness, and selected-global entry points. Missing required bindings mean unavailable transport, not silent fallback. |

For `user` setup, its own ownership block is user-local and does not replace primary setup. Host preference changes do not require primary activation, an idle project inventory, or fencing unrelated reviews. New runs seal resolved preferences and observations into their own provenance; an existing run retains its recorded command/session contract and permits model/effort changes only through its existing explicit provider-resume protocol. New preference bytes never silently redirect an active review. No tracked portable config may contain machine command paths or per-developer identity hints. Migration inventories existing primary/user host fields, shows each destination, and refuses ambiguous collisions; it moves machine values only to the explicit invoking user's untracked config with consent through the maintenance action, preserving before-bytes. Primary policy is never overwritten by a user's legacy policy values.

The public `configPaths` result includes `project` as the primary file path, `primaryRoot`, and `activeWorktreeRoot`. Outside Git, `project` and both roots are `null`; user setup reads only user config, while project mutation refuses missing identity. This is a documented public API change. The loader rejects invalid, unreadable, or symlinked primary config rather than treating it as absent. The primary config may be absent only for an explicitly uninitialized registration; initial primary-only project setup creates it through the normal ownership rules. Missing files in an initialized clone refuse normal mutation. A conflicting linked-worktree config is diagnostic data only and cannot complete a missing primary field.

Project `setup`, `setup --update`, and `setup --remove` target only the primary checkout's owned config and host integration files. The current global installation already supports `setup --update`; this design extends its existing setup-scope refresh and conflict safeguards to the primary-workspace layout. A linked-worktree invocation reports the primary path, branch, and changed owned paths, then refuses apply with the exact command to run from the primary checkout. This design provides no cross-worktree setup override; `setup`, update, removal, registration repair, and policy activation that write primary tracked files must be invoked in the validated primary checkout. User-scope setup remains separate. On every `setup`, the current installed package regenerates only its owned config fields, skill, and hook portions and writes them if bytes change; an idempotent run need not rewrite identical bytes. User-authored `authority`, `hosts`, and `review` settings remain under user control and are validated, not reset to package defaults. Setup migrates an older owned layout to the current one rather than asking the runtime to support every old config or skill schema. Existing foreign-file and ownership protections remain; unrelated provider settings are preserved. No setup operation writes an exact AIPR package version requirement. The legacy `setup.package_version` field can be read for migration but is no longer a gate requiring the current global version to equal old copied setup metadata; its presence must not silently bless a stale copied skill or hook.

Package-owned host integrations must invoke the registered global CLI/hook entry points. For linked worktrees, the preferred discovery route is one user-scope, package-owned Codex/Claude skill wrapper that calls the registered global tool to resolve the caller's Git common directory and primary shared skill. Project-local discovery files in the primary checkout remain available for that checkout. If a host cannot discover the user-scope wrapper from a linked worktree, a verified pointer to the primary integration is required; merely writing a wrapper in the primary checkout does not make it discoverable from every linked worktree. The implementation plan must choose and prove the host-specific mechanism on supported platforms, including missing user-scope setup, different clones, and a stale linked-worktree copy. An unavailable or ambiguous discovery route refuses review and gives a setup repair command rather than using a stale tracked copy. A foreign or conflicting tracked integration is reported and preserved, not replaced on `doctor`. A global AIPR upgrade may require one primary or user-scope integration refresh if the integration contract changed; it must never imply one refresh per linked worktree. Read-only doctor reports this separately from runtime compatibility.

## Integration currency

The installed package declares one integration contract in its runtime compatibility assets: a contract identifier, the digest of the package-owned shared skill body, deterministic thin-wrapper templates, and normalized owned hook command portions for each supported host. The primary activation receipt records the generated contract and owned digests. `assertProjectSetupCompatible` is replaced internally by a contract-and-owned-content check at every governed mutation and after asynchronous waits; doctor runs the same check read-only. Compare the installed contract with the activated primary shared body, the discoverable user/primary wrapper, and package-owned hook portions. Preserve foreign settings and exclude them from these digests.

An upgrade whose integration contract and generated owned content are unchanged requires no refresh regardless of package version. Missing, modified, unsupported, or mismatched owned integrations return the retained `APR_SETUP_VERSION_MISMATCH` code with integration-contract semantics and a primary/user-scope `setup --update --dry-run` then `setup --update` repair command. Refresh from the primary, commit changed owned project files, and activate their new blobs before review mutation. A legitimately changed shared procedure is a new integration contract, not an arbitrary branch override. Source-development tests exercise alternate bodies only inside the explicit fixture harness. Bootstrap and repair commands are distinct narrow maintenance operations: user-scope runtime registration validates the executing installation without requiring an existing selection; primary registration validates Git identity without requiring existing project integration; setup dry-run/update validates ownership and current before-bytes without requiring the old integration to match the new contract; activation validates newly committed blobs and the current contract rather than requiring their equality with the prior receipt. These operations still enforce caller/target identity, conflict refusal, inventory, atomicity, and read-back, and cannot launch or continue a review while its prerequisites are unavailable. Normal review mutations have no maintenance exception.

## Central project files and format contracts

The primary checkout stores tracked AIPR-owned project files under `.ai-peer-review/`. Move the legacy `.ai-peer-review.json` to `.ai-peer-review/config.json`; loaders and setup do not keep writing both. A migration inventories the old and new paths, refuses conflicting copies or unknown ownership, reports its dry-run actions, and preserves the old file until a safe explicit migration can remove it. Linked worktree copies are never independent authorities. The primary file is the only project configuration read for every linked worktree, subject to the existing physical-worktree mutation check.

Move AIPR-neutral setup metadata currently copied into `.codex/config.json` into the primary `.ai-peer-review/config.json` or a single AIPR-owned companion there. The current checkout has no `.claude/config.json` counterpart. A provider directory should contain only a file the provider itself requires for discovery or hook registration. Provider-native hooks stay in `.codex/hooks.json` and `.claude/settings.json` because their formats differ; preserve unrelated provider settings and foreign ownership. If a future provider requires a local AIPR config file, it is a minimal pointer/projection with a declared schema and no duplicated canonical values.

The canonical provider-neutral skill body lives once at `.ai-peer-review/SKILL.md` in the registered primary checkout. Each required `.codex/skills/peer-review/SKILL.md` or `.claude/skills/peer-review/SKILL.md` is a thin discovery wrapper with valid host metadata. It directs the agent to load the primary shared body before review work and fails closed when that body cannot be resolved or verified. Provider-only instructions may live in the wrapper or an explicitly loaded provider addendum; the generic procedure is not duplicated. A plain relative path into a linked worktree is insufficient because it may select stale branch content. The host adapter must resolve the registered primary, or use a verified global CLI command that emits the selected shared instructions. Host integration tests must establish that Codex and Claude actually load the shared body; documentation about linked files alone does not prove automatic inclusion. Avoid relying on symlink behavior across hosts and Windows unless those tests prove it.

The installed package ships a versioned compatibility manifest beside its runtime code. Its primary purpose is to declare which durable **review session collateral** layouts and content schemas the current package can read and safely continue: review records and attempts, event journals, invitations, responses, snapshots, archive structure, and any persisted runtime-image or broker state required to resume that review. It declares a closed supported-version set or minimum and maximum for each independently evolving review contract. A minimum alone cannot safely accept an unknown future schema. Review files declare schema/layout versions; legacy unversioned material maps to a version only after exact shape validation. The executing package validates its own manifest and the prior review before continuing or mutating it. The manifest describes review compatibility, not a project pin to a package version. AIPR-owned portions of config, skill, and hook files are regenerated to the current installed package format on `setup`; user-authored configuration and foreign provider settings are preserved. These setup surfaces require migration and validation of owned content, not a matrix of old versions for ongoing review operation. Installed-artifact tests cover supported older review collateral, unknown/future formats, incomplete manifests, setup refresh from older owned files, and global upgrade behavior.

Legacy inventory distinguishes owned primary migration inputs from non-authoritative linked copies. Doctor reports pre-migration linked `.ai-peer-review.json` files and `.bak` siblings as known legacy/backup inventory with bounded path-only diagnostics. It reports a conflicting owned primary old/new pair as a migration blocker, but a known linked legacy file is not a runtime conflict on every invocation. Setup never removes linked copies or backup files automatically. Their repository owner may remove them through an ordinary tracked change after primary migration is accepted.

## Tracked setup files and host formatting

Every durable file that AIPR creates or updates in a host repository must be ready to commit: primary `.ai-peer-review/config.json` and `.ai-peer-review/SKILL.md`, provider skill wrappers, provider config projections where required, and AIPR-owned portions of hook/settings files. Setup, update, removal, and migration use deterministic, valid JSON or Markdown serialization, including a final newline and stable ordering. The output must pass AIPR's published formatting and lint reference checks. Setup must not require the user to edit installed package scripts, run AIPR's source test suite, or manually reformat AIPR-generated files after every operation.

The npm package includes a small, versioned copy of the formatting and lint rules that govern these shipped/generated file types, plus instructions for running an installed-file check. These are reference assets for a host repository that lacks equivalent rules; they are not development scripts or a command to rewrite the host's lint configuration. AIPR does not install Prettier or lint packages into the host, replace its configs, or change unrelated files. Keep the reference rules aligned with the source repository rules through source CI and tarball inspection.

Before applying a tracked-file setup change, AIPR stages the proposed bytes in an isolated temporary area and checks its own reference rules. It also detects the host's configured formatter and linter, when available, and validates only the files it proposes to change under those host rules. A host check must use the effective configuration and ignore behavior for each intended destination path, not accidentally pass because temporary paths are outside the host lint scope. If compatible formatting can be produced without changing AIPR semantics or foreign-owned content, setup writes those bytes atomically. If the host rules conflict, or a required host check cannot be run reliably, setup reports the exact files and command/reason and leaves the tracked files unchanged; it does not silently claim that arbitrary host-specific lint rules passed. Validation must not run a repository-wide fix or make CI depend on a global AIPR installation. The implementation plan must define and test how mixed-ownership JSON such as `.claude/settings.json` is checked without reformatting unrelated settings, and how pre-existing host lint failures are distinguished from new AIPR-generated failures.

## Project-local dependencies and CI boundary

Each project checkout and linked worktree retains its own `node_modules` for that project's dependencies and branch-specific development needs. AIPR setup, doctor, and review commands never link, replace, delete, or install those dependencies. The project-local tree is not an AIPR runtime selector. If an older `@kburson/ai-peer-review` happens to be present there, it is not used for governed review mutations; a source checkout can still run its own code for package development tests under an explicit test harness. Production review mutations from that source or local installation refuse unless it is the registered current global installation. There is no caller-supplied bypass flag.

AIPR is a planning-time tool on the developer or agent host. Consumer projects' cloud CI and runtime builds do not need a global AIPR installation, clone-local registration, `peer-review doctor`, or a review gate. Merely checking out a repository with `.ai-peer-review/config.json` cannot make its normal tests or deployment depend on AIPR. If a CI job explicitly invokes an AIPR command, that job has intentionally opted into provisioning and checking the tool.

Only the `ai-peer-review` **source repository and its CI** run unit, integration, packaging, and installed-artifact compatibility tests. The published npm tarball contains runtime code, required runtime assets, and a runtime-only package manifest; it excludes `test/`, test fixtures, repository release/packaging verifiers, and development-only npm scripts such as test, lint, format, and release checks. A user installs and invokes the global tool without editing package scripts or running its test suite. Source CI assembles and inspects the tarball in an isolated fixture; it does not modify the machine's real global npm installation. The current tarball allowlist includes `scripts/verify-extraction.mjs` and `scripts/verify-release.mjs`, and the current packaging test expects them. These two historical provenance verifiers depend on the source Git repository and fixed v0.2.0 release evidence; they do not verify a user installation or setup. Keep them in source CI, outside the installed package. Ship a distinct deployment verifier as part of the CLI or a runtime-only script that checks the installed artifact, compatibility manifest, global registration, and project/provider setup without requiring source files, test fixtures, or release tooling. `doctor --mode installation` may expose this verification. Its diagnostics must be safe and read-only. The native broker build helper is a separate installation dependency until #107's install-ready runtime replaces it; it is not a test or release verifier.

## Global selection record and digest observations

Store global selection once in a fixed account-derived platform directory as a separate owner-only `runtime-selection.json` record, shared by every repository clone. For authority-bearing selection, derive the account home/profile from the OS account API (POSIX account database or Windows account/profile API), not `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, or `APPDATA`. Use the fixed `.config/ai-peer-review/runtime-selection.json` under that account home on POSIX and the fixed account LocalAppData AIPR directory on Windows; refuse if the account directory cannot be verified. Environment-directed user preference locations may remain supported for non-authoritative preferences, but never select a production runtime or primary registration. Authority-bearing Git discovery executes with caller `GIT_*` directory, worktree, index, object, configuration and environment overrides removed, uses the physical invoking worktree, and validates the returned common directory against its on-disk `.git` identity and worktree membership. A caller environment cannot redirect clone registration. Alternate selection/registration records are available only to an explicit internal source fixture harness that cannot launch production provider work. It contains a closed schema, a random `selection_id`, canonical `package_root`, canonical `node_executable`, package name, and registration receipt time. Clone primary registrations do not duplicate these locator fields or constrain a version. The observed package version, content digest, Node version, and creation-time filesystem identities are provenance; they are not persisted equality requirements that would reject an in-place upgrade. Every entry point compares its actual executing package root, package name, and Node executable with the current selection locator, then validates current files and records their observations. A routine Node-manager relocation needs one explicit user-scope selection update and read-back for all clones; it never needs one update per clone. #130's machine receipts must consume this same split rather than introduce clone-specific runner pins.

The installed runtime manifest declares a bounded, sorted relative inventory covering executing JS modules, runtime schemas/templates, provider adapters, compatibility/integration assets, and any required native helper identity. Reject traversal, links, missing/extra declared executable files, invalid metadata, and files that change while observed. An invocation seals the selected record generation and inventory digest. Before later effects, re-check the selection generation and file identities and recompute the bounded inventory when identities change; compare with the sealed process image before effect admission. A process-wide verified observation may serve multiple checks while identities are unchanged, but no observation survives an asynchronous wait without revalidation. An npm replacement during observation refuses with a retry diagnostic rather than accepting mixed bytes. Source benchmarks cover startup, hook, and repeated-effect cost with this declared inventory; there is no full recursive filesystem scan at every effect.

## Current runtime and review compatibility

The registered global installation is selected by canonical package root and Node executable, not by `PATH`, cwd, an environment variable, a local dependency, or a caller-provided version string. At each entry point, derive package identity from the executing module and the supported durable review collateral formats from its packaged compatibility manifest. Current provider integration formats come from the installed package and are refreshed by `setup`. Compare the real executing path with the registration. An in-place global upgrade retains the path but changes observed package metadata and installed-file digest; no config version edit is required. A relocated global installation needs one explicit user-scope re-registration shared by all clones. Seal the executing process's package-file digest at startup and compare the on-disk global installation before later effects. If npm replaces files while an old process remains alive, that process fences further mutation; a fresh invocation loads and checks the new code. Invalid package metadata, incomplete installation, or a changed/unsafe path refuses mutation.

At review start, seal the current package version, installation identity, format versions, and worktree identity in the run authority. These are provenance and compatibility inputs, not a request to keep an old executable. Before each state-changing operation, inspect the recorded formats and the current package's declared supported-format matrix. A match admits the operation only after existing identity, provider, Git, ownership, and protocol gates pass. An unknown or unsupported prior-review format returns `APR_REVIEW_RUNTIME_UNSUPPORTED` with the observed package, recorded collateral format identifiers, review path, and safe guidance. Version equality alone neither proves compatibility nor grants authority. If an older collateral format becomes supported by a later package, that support must be explicit and covered by installed-artifact tests; no automatic journal rewrite is implied. If the current package cannot understand the prior review, it preserves that review read-only and reports it as incompatible through a separate diagnostic; it cannot safely declare the old attempt terminal in an unknown journal. A new review of the current file-under-review may start under the current format only after the caller selects independent review paths/IDs and ordinary Git, issue, identity, and broker gates pass. In particular, an old output or scratch reservation is never overwritten or released merely to make the new review possible; the operator can use an independent reviews root/path template, or a future proven migration/disposition path. The new review records a reference to the preserved predecessor outside the predecessor collateral and must not silently treat it as complete. Any terminal supersession or abandonment of the old attempt requires a separately proven safe operation; incompatibility alone cannot authorize a blind write to its journal.

Existing runtime images remain immutable evidence and can be validated for integrity, but an image may execute only when its verified package-file digest and Node identity equal the **currently selected global installation** for the same run and operation. Version-string equality alone is insufficient. An older image is not a fallback after upgrade, even if its files or a worktree-local AIPR package still exist. Broker startup, worker restoration, offline reconciliation, MCP, hooks, and exported state writers independently enforce the current-installation and supported-format checks before effects. A mismatched older image cannot be launched to make `status`, `doctor`, or cleanup appear successful.

If the global package changes while work is in progress, the next effect boundary revalidates the current installation and format support. A supported new runtime may continue under the same review authority; an unsupported one fences new work, preserves all existing evidence, and provides read-only status. Owned stop/suspend/cancellation is permitted only when the current runtime can prove the existing broker's protocol, root, and ownership; otherwise it reports that safe cleanup is unavailable. It never launches an older image or kills a process by PID guess. No package can guarantee an operator will not replace a global npm installation mid-operation; the guarantee is fail-closed admission and revalidation at subsequent mutation boundaries.

## Diagnostics and rollout

Doctor shows independent rows for primary registration/config, selected global package, copied integration compatibility, current review format support when a review is named, provider identity, and broker health. `doctor --mode installation` does not require a current provider/model. It reports physical paths and bounded reasons without dumping environment/config or executing candidate packages. Help and explain work without Git. Status and other read-only inspection keep their successful stdout schemas and report unsupported runtime separately on stderr or structured diagnostic fields already allowed by their schema. Diagnosis never installs, fetches, rewrites a review, or starts a broker. For unparseable or unsupported collateral, status reports only canonical review path, independently readable declared schema/layout identifiers, and a bounded unsupported/invalid reason. State, decision, participants, and sequence are unknown unless a supported parser validates them; status never performs a best-effort reduction of an unknown journal or infers terminality from filenames.

Rollout first registers the primary checkout and current global installation for each local clone, validates the primary config, then refreshes primary/user integrations. Each linked worktree resolves that same config before review mutation; its project dependencies remain local. Existing review state is inventoried before a global update where possible; an operator can finish or settle incompatible reviews before upgrading. After an uncoordinated upgrade, unsupported reviews stay fenced rather than silently using a retained old package; a fresh review of the current file-under-review may begin under the new collateral format with independent identity and paths. Primary setup preserves foreign and unrelated edits. The old exact-pin spec, proposed `--pin-tool-version` modes, policy locks, and per-worktree pin tests are not implemented.

The runtime-only tarball boundary and packaged deployment verifier belong with #107's install-ready package work; #102 requires its verification before release and does not ask installed users to run repository test or packaging scripts. #128's current JSON formatting fix is retained, while #102 verifies all generated tracked setup files against destination-effective rules. #111 owns historical collateral lint and layout migration; #102 consumes its versioned outcomes without rewriting that evidence. #130 owns the detailed shared-config and receipt contract subject to this design's selected-global-runtime and active-worktree boundaries. The #107 proposal currently assigns same-worktree legacy routing to older pinned installations. That ownership is incompatible with this decision. #107 must instead specify what the current installation supports and how unsupported legacy reviews remain inspectable/fenced; it may not route to an older package merely because an image or local dependency remains. #115/#117 recovery fixes remain valid for reviews whose selected runtime and formats are supported; their older-image fallback paths require an explicit compatibility audit before this design ships.

## Acceptance criteria for the replacement #102 scope

1. A validated primary registration resolves one project config for primary, linked, and subdirectory invocations; missing/moved/foreign/ambiguous primary state, dirty/staged/unmerged owned files including during merge/rebase, and pre-migration or different-policy branch changes refuse project mutation. Identical activated blobs on another branch remain valid. Worktree-local config cannot override or deep-merge it.
2. Existing user config and user setup work outside Git; project setup and all project config sections use the primary checkout and preserve owned/foreign boundaries. Project authority/review/setup and classified host policy are primary-exclusive; user-exclusive host identity hints and command/timing bindings use the field-ownership table and cannot override policy or identity proof. Preferences need no primary activation and cannot silently redirect existing runs. Linked-worktree setup apply refuses and identifies the primary-only command.
3. Each primary or linked worktree may keep its own project-local `node_modules`; AIPR never rewrites, links, deletes, or treats that directory as runtime authority. Consumer CI and runtime builds do not require AIPR installation or a review/doctor gate.
4. The selected global package is identified by its executing module and registered canonical path; cwd, PATH, env, source checkout, local dependency, and API inputs cannot impersonate it. Global in-place upgrades do not require exact project version or selection-record edits. A Node/global-path relocation updates one user-scope selection record for all clones; the registration comparison fields and provenance-only fields are explicit. OS-account selection location and scrubbed Git discovery reject caller environment redirection.
5. The current package's packaged compatibility manifest primarily governs durable prior-review collateral layout and content, alongside sealed review provenance and existing authority checks. Unsupported/unknown old review formats and invalid metadata fail before effects; supported formats continue only with existing integrity checks. An incompatible prior review remains preserved and can be identified as deprecated/incompatible without rewriting it; a new review of the current file-under-review uses independent identity and paths.
6. Older runtime images and worktree-local packages remain evidence or development artifacts and are never executed as an upgrade fallback. Broker, hooks, MCP, and exported writers enforce the same rule, including after async waits.
7. Unsupported review cleanup is bounded to proven current-runtime ownership and protocol; otherwise evidence remains and the operation refuses without guessing or launching older code.
8. Doctor distinguishes registration, config, selected package, integration, format support, identity, and broker health; read-only commands preserve successful output schemas and have no effects.
9. Each `setup` regenerates package-owned config fields, skill, and hook portions to the current installed format while preserving user-authored and foreign settings, writing only changed bytes; setup migration is explicit and idempotent, moves `.ai-peer-review.json` to primary `.ai-peer-review/config.json`, centralizes AIPR-neutral setup metadata and skill instructions, changes primary/user integrations once per clone or user, and preserves foreign files and active review evidence. Thin host skill wrappers must demonstrably load the registered primary shared body. Every mutation checks the declared integration contract and owned-content digests; an unchanged-contract upgrade needs no refresh. Primary setup refuses dirty owned files and writes only from the primary; activation requires committed owned blobs, read-back, and safe active-review inventory. Linked experimental policy is tested in isolated fixtures. A source/local runner cannot bypass global selection.
10. Every tracked AIPR setup output passes the package reference format/lint rules and applicable host file checks before atomic write; setup does not introduce formatter/lint failures, alter the host toolchain, or require manual formatting. The package includes the versioned reference rules and an installed-file check. Host-rule conflicts refuse with specific diagnostics and no partial tracked-file changes.
11. Source-repository CI inspects the exact published tarball and its package manifest: no tests, fixtures, development npm scripts, or source-release/packaging verifier tools ship; the runtime compatibility manifest, deployment verifier, and formatting/lint reference assets do ship. Installed-artifact fixtures cover global upgrade, changed Node/global path, active and terminal older reviews, ordinary/linked/custom Git layouts, paths with spaces, and Windows and POSIX without real global-install or registry mutation. Consumer-project CI fixtures pass without AIPR installed. Include primary branch switches to pre-migration/different/identical-blob branches, dirty/staged owned primary files, unrelated and owned-file merge/rebase cases, linked setup refusal, multi-clone Node-manager relocation, field-level policy/preference precedence and sealed preference continuity, `HOME`/`USERPROFILE`/`XDG_CONFIG_HOME`/`APPDATA` selection redirection, `GIT_DIR`/`GIT_COMMON_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` registration redirection, unchanged/changed integration contracts, pulled-policy activation diagnostics, and bounded status of unreadable journals.

## Open implementation sequencing, not design authority

Plan work in independently verifiable slices: primary registration/config; global runner selection and integration migration; review-format support and old-image fence; cross-entry-point enforcement; installed-artifact matrix. The implementation plan must map each criterion to tests and preserve the existing #102 review trail. No implementation begins from the superseded exact-pin plan.
