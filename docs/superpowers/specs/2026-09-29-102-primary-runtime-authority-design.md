# Primary-Workspace AIPR Runtime Authority Design

## Status and provenance

- Issue: [#102](https://github.com/kburson/ai-peer-review/issues/102).
- Status: draft replacement for `2026-09-26-102-aipr-install-policy-design.md`. The earlier accepted XPR remains historical evidence for its earlier requirements; it does not approve this design.
- User decision: one primary-checkout AIPR config per repository clone, project-local dependencies in each checkout, one current global AIPR installation on the planning host, and **no exact project package-version pin**. A globally replaced version is not treated as available through a worktree-local package or retained runtime image.
- Planning boundary: revise #102's issue scope and acceptance criteria only after this design is accepted. The superseded implementation-plan draft must not be executed. #107's per-run older-installation routing proposal must also be reconciled before it is implemented.

## Problem and outcome

The earlier #102 design made each physical worktree's legacy `.ai-peer-review.json` an independent exact package-version authority. That would require repeated config changes when one global installation changes, and it implies that an older worktree-local installation could still be selected. Neither behavior matches the intended operating model.

For one Git repository clone, the primary checkout owns the project AIPR configuration and shared skill instructions. Linked worktrees use that config while retaining their own project-local `node_modules` for their own dependencies. AIPR review mutations use the currently registered global AIPR package on the planning host. The active review worktree remains the authority for its Git state, review files, provider sessions, and broker ownership. An upgrade never silently replays an old review with a stored older executable.

Success means a global update requires no version-pin edit in each project or worktree. The updated runtime either proves it supports an existing review's recorded format and operation or refuses mutation with intact evidence. Stale copied integrations and divergent source checkouts cannot bypass that check.

## Authority domains

| Domain                   | Authority                                                                                  | Boundary                                                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository identity      | Validated Git common directory                                                             | Groups primary and linked worktrees of one clone only.                                                                                                         |
| Primary checkout         | Clone-local primary registration under the common Git administrative directory             | Stores a canonical path and Git identity; no inference from current directory name or a sibling config.                                                        |
| Project config           | Primary checkout's `.ai-peer-review/config.json`                                           | All config sections (`authority`, `hosts`, `review`, `setup`) come from this one file. No `tool.required_version` or other exact package pin.                  |
| Selected AIPR runner     | Clone-local registration of a canonical, installed global package path and Node executable | Registration records paths and installation identity, not a required version. Every invocation checks that its executing module is that selected installation. |
| Review and Git state     | Physical worktree in which the review was started                                          | Review artifacts, runtime observations, Git snapshots, scratch, and broker ownership do not move to the primary checkout.                                      |
| Historical runtime image | Immutable review evidence                                                                  | An image with older package bytes is never an alternate executable after a global update.                                                                      |

The clone-local registration is machine state, not a tracked project file. Put it under the validated Git common administrative directory with owner-only permissions, an explicit schema, atomic writes, and an installation/primary-path change receipt. The tracked primary config remains portable across machines. A bare repository, absent primary checkout, moved primary checkout, missing registration, unreadable registration, foreign worktree, or ambiguous ownership fails closed for project mutation. `help` and `explain` remain available without Git. User-scoped setup outside Git remains available without consulting a project config.

The registration command accepts a primary checkout only when it is the validated main worktree of that common directory. It records the real path and Git common-directory identity, then reads it back before reporting success. It never adopts a linked worktree merely because a caller labels it primary. Registration of a replacement primary requires an explicit operator action, a dry-run diff, and a read-only inventory of active reviews; it does not move or rewrite review evidence. A primary path that no longer validates remains unavailable until repaired explicitly.

## Configuration and setup

`configPaths` and `loadConfig` resolve the caller's physical worktree, validate its Git common directory, locate the registered primary checkout, and read the primary `.ai-peer-review/config.json`. Subdirectory and linked-worktree invocations therefore use the same project file. A same-named file in a linked worktree is ignored as project authority and diagnosed if it conflicts. It is not merged. User config retains its existing per-user path and merge precedence for unrelated settings; project setup ownership and every project config section come from the primary file. An explicit workspace or invitation path must still agree with the caller's validated physical worktree; a shared config cannot authorize cross-worktree review mutation.

The public `configPaths` result includes `project` as the primary file path, `primaryRoot`, and `activeWorktreeRoot`. Outside Git, `project` and both roots are `null`; user setup reads only user config, while project mutation refuses missing identity. This is a documented public API change. The loader rejects invalid, unreadable, or symlinked primary config rather than treating it as absent. The primary config may be absent for a new clone; initial project setup creates it through the normal ownership rules. A conflicting linked-worktree config is diagnostic data only and cannot complete a missing primary field.

Project `setup`, `setup --update`, and `setup --remove` target only the primary checkout's owned config and host integration files. A linked-worktree invocation resolves that target and reports it before apply. User-scope setup remains separate. Existing foreign-file and ownership protections remain. No setup operation writes an exact AIPR package version requirement. The legacy `setup.package_version` field can be read for migration but is no longer a gate requiring the current global version to equal old copied setup metadata; its presence must not silently bless a stale copied skill or hook.

Package-owned host integrations must invoke the registered global CLI/hook entry points. Where a host requires project-local discovery, a linked worktree uses a verified pointer to the primary integration, or a supported user-scope integration; it must not run a stale tracked copy as current package code. The implementation plan must choose the host-specific mechanism from observed Codex/Claude behavior and test it on supported platforms. A foreign or conflicting tracked integration is reported and preserved, not replaced on `doctor`. A global AIPR upgrade may require one primary or user-scope integration refresh if the integration contract changed; it must never imply one refresh per linked worktree. Read-only doctor reports this separately from runtime compatibility.

## Central project files and format contracts

The primary checkout stores tracked AIPR-owned project files under `.ai-peer-review/`. Move the legacy `.ai-peer-review.json` to `.ai-peer-review/config.json`; loaders and setup do not keep writing both. A migration inventories the old and new paths, refuses conflicting copies or unknown ownership, reports its dry-run actions, and preserves the old file until a safe explicit migration can remove it. Linked worktree copies are never independent authorities. The primary file is the only project configuration read for every linked worktree, subject to the existing physical-worktree mutation check.

Move AIPR-neutral setup metadata currently copied into `.codex/config.json` into the primary `.ai-peer-review/config.json` or a single AIPR-owned companion there. The current checkout has no `.claude/config.json` counterpart. A provider directory should contain only a file the provider itself requires for discovery or hook registration. Provider-native hooks stay in `.codex/hooks.json` and `.claude/settings.json` because their formats differ; preserve unrelated provider settings and foreign ownership. If a future provider requires a local AIPR config file, it is a minimal pointer/projection with a declared schema and no duplicated canonical values.

The canonical provider-neutral skill body lives once at `.ai-peer-review/SKILL.md` in the registered primary checkout. Each required `.codex/skills/peer-review/SKILL.md` or `.claude/skills/peer-review/SKILL.md` is a thin discovery wrapper with valid host metadata. It directs the agent to load the primary shared body before review work and fails closed when that body cannot be resolved or verified. Provider-only instructions may live in the wrapper or an explicitly loaded provider addendum; the generic procedure is not duplicated. A plain relative path into a linked worktree is insufficient because it may select stale branch content. The host adapter must resolve the registered primary, or use a verified global CLI command that emits the selected shared instructions. Host integration tests must establish that Codex and Claude actually load the shared body; documentation about linked files alone does not prove automatic inclusion. Avoid relying on symlink behavior across hosts and Windows unless those tests prove it.

The installed package ships a versioned compatibility manifest beside its runtime code. It declares a closed supported-version set or minimum and maximum for each independent contract: project config, AIPR host setup metadata, Codex and Claude hook surfaces, shared skill and each host wrapper, review collateral format/layout, runtime image, and broker/MCP protocols. A minimum alone cannot safely accept an unknown future schema. Files or review records declare their own schema IDs; legacy unversioned material maps to a version only after exact shape validation. The executing package reads and validates its own manifest and refuses unknown, malformed, or unsupported formats before effects. The manifest describes compatibility, not a project pin to a particular package version. Installed-artifact tests cover current and older supported fixtures, future/unknown versions, incomplete manifests, and global upgrade behavior.

## Tracked setup files and host formatting

Every durable file that AIPR creates or updates in a host repository must be ready to commit: primary `.ai-peer-review/config.json` and `.ai-peer-review/SKILL.md`, provider skill wrappers, provider config projections where required, and AIPR-owned portions of hook/settings files. Setup, update, removal, and migration use deterministic, valid JSON or Markdown serialization, including a final newline and stable ordering. The output must pass AIPR's published formatting and lint reference checks. Setup must not require the user to edit installed package scripts, run AIPR's source test suite, or manually reformat AIPR-generated files after every operation.

The npm package includes a small, versioned copy of the formatting and lint rules that govern these shipped/generated file types, plus instructions for running an installed-file check. These are reference assets for a host repository that lacks equivalent rules; they are not development scripts or a command to rewrite the host's lint configuration. AIPR does not install Prettier or lint packages into the host, replace its configs, or change unrelated files. Keep the reference rules aligned with the source repository rules through source CI and tarball inspection.

Before applying a tracked-file setup change, AIPR stages the proposed bytes in an isolated temporary area and checks its own reference rules. It also detects the host's configured formatter and linter, when available, and validates only the files it proposes to change under those host rules. If compatible formatting can be produced without changing AIPR semantics or foreign-owned content, setup writes those bytes atomically. If the host rules conflict, or a required host check cannot be run reliably, setup reports the exact files and command/reason and leaves the tracked files unchanged; it does not silently claim that arbitrary host-specific lint rules passed. Validation must not run a repository-wide fix or make CI depend on a global AIPR installation. The implementation plan must define and test how mixed-ownership JSON such as `.claude/settings.json` is checked without reformatting unrelated settings, and how pre-existing host lint failures are distinguished from new AIPR-generated failures.

## Project-local dependencies and CI boundary

Each project checkout and linked worktree retains its own `node_modules` for that project's dependencies and branch-specific development needs. AIPR setup, doctor, and review commands never link, replace, delete, or install those dependencies. The project-local tree is not an AIPR runtime selector. If an older `@kburson/ai-peer-review` happens to be present there, it is not used for governed review mutations; a source checkout can still run its own code for package development tests under an explicit test harness. Production review mutations from that source or local installation refuse unless it is the registered current global installation. There is no caller-supplied bypass flag.

AIPR is a planning-time tool on the developer or agent host. Consumer projects' cloud CI and runtime builds do not need a global AIPR installation, clone-local registration, `peer-review doctor`, or a review gate. Merely checking out a repository with `.ai-peer-review/config.json` cannot make its normal tests or deployment depend on AIPR. If a CI job explicitly invokes an AIPR command, that job has intentionally opted into provisioning and checking the tool.

Only the `ai-peer-review` **source repository and its CI** run unit, integration, packaging, and installed-artifact compatibility tests. The published npm tarball contains runtime code, required runtime assets, and a runtime-only package manifest; it excludes `test/`, test fixtures, repository release/packaging verifiers, and development-only npm scripts such as test, lint, format, and release checks. A user installs and invokes the global tool without editing package scripts or running its test suite. Source CI assembles and inspects the tarball in an isolated fixture; it does not modify the machine's real global npm installation. The current tarball allowlist includes `scripts/verify-extraction.mjs` and `scripts/verify-release.mjs`, and the current packaging test expects them. These two historical provenance verifiers depend on the source Git repository and fixed v0.2.0 release evidence; they do not verify a user installation or setup. Keep them in source CI, outside the installed package. Ship a distinct deployment verifier as part of the CLI or a runtime-only script that checks the installed artifact, compatibility manifest, global registration, and project/provider setup without requiring source files, test fixtures, or release tooling. `doctor --mode installation` may expose this verification. Its diagnostics must be safe and read-only. The native broker build helper is a separate installation dependency until #107's install-ready runtime replaces it; it is not a test or release verifier.

## Current runtime and review compatibility

The registered global installation is selected by canonical package root and Node executable, not by `PATH`, cwd, an environment variable, a local dependency, or a caller-provided version string. At each entry point, derive name/version and supported authority, review, runtime-image, broker-protocol, hook, and MCP formats from a packaged compatibility manifest belonging to the package containing the executing module. Compare the real executing path with the registration. An in-place global upgrade retains the path but changes observed package metadata and installed-file digest; no config version edit is required. A relocated global installation needs explicit re-registration. Seal the executing process's package-file digest at startup and compare the on-disk global installation before later effects. If npm replaces files while an old process remains alive, that process fences further mutation; a fresh invocation loads and checks the new code. Invalid package metadata, incomplete installation, or a changed/unsafe path refuses mutation.

At review start, seal the current package version, installation identity, format versions, and worktree identity in the run authority. These are provenance and compatibility inputs, not a request to keep an old executable. Before each state-changing operation, inspect the recorded formats and the current package's declared supported-format matrix. A match admits the operation only after existing identity, provider, Git, ownership, and protocol gates pass. An unknown or unsupported format returns `APR_REVIEW_RUNTIME_UNSUPPORTED` with the observed package, recorded format identifiers, review path, and safe guidance. Version equality alone neither proves compatibility nor grants authority. If an older format becomes supported by a later package, that support must be explicit and covered by installed-artifact tests; no automatic journal rewrite is implied.

Existing runtime images remain immutable evidence and can be validated for integrity, but an image may execute only when its verified package-file digest and Node identity equal the **currently selected global installation** for the same run and operation. Version-string equality alone is insufficient. An older image is not a fallback after upgrade, even if its files or a worktree-local AIPR package still exist. Broker startup, worker restoration, offline reconciliation, MCP, hooks, and exported state writers independently enforce the current-installation and supported-format checks before effects. A mismatched older image cannot be launched to make `status`, `doctor`, or cleanup appear successful.

If the global package changes while work is in progress, the next effect boundary revalidates the current installation and format support. A supported new runtime may continue under the same review authority; an unsupported one fences new work, preserves all existing evidence, and provides read-only status. Owned stop/suspend/cancellation is permitted only when the current runtime can prove the existing broker's protocol, root, and ownership; otherwise it reports that safe cleanup is unavailable. It never launches an older image or kills a process by PID guess. No package can guarantee an operator will not replace a global npm installation mid-operation; the guarantee is fail-closed admission and revalidation at subsequent mutation boundaries.

## Diagnostics and rollout

Doctor shows independent rows for primary registration/config, selected global package, copied integration compatibility, current review format support when a review is named, provider identity, and broker health. `doctor --mode installation` does not require a current provider/model. It reports physical paths and bounded reasons without dumping environment/config or executing candidate packages. Help and explain work without Git. Status and other read-only inspection keep their successful stdout schemas and report unsupported runtime separately on stderr or structured diagnostic fields already allowed by their schema. Diagnosis never installs, fetches, rewrites a review, or starts a broker.

Rollout first registers the primary checkout and current global installation for each local clone, validates the primary config, then refreshes primary/user integrations. Each linked worktree resolves that same config before review mutation; its project dependencies remain local. Existing review state is inventoried before a global update where possible; an operator can finish or settle incompatible reviews before upgrading. After an uncoordinated upgrade, unsupported reviews stay fenced rather than silently using a retained old package. Primary setup preserves foreign and unrelated edits. The old exact-pin spec, proposed `--pin-tool-version` modes, policy locks, and per-worktree pin tests are not implemented.

The runtime-only tarball boundary and packaged deployment verifier belong with #107's install-ready package work; #102 requires its verification before release and does not ask installed users to run repository test or packaging scripts. The #107 proposal currently assigns same-worktree legacy routing to older pinned installations. That ownership is incompatible with this decision. #107 must instead specify what the current installation supports and how unsupported legacy reviews remain inspectable/fenced; it may not route to an older package merely because an image or local dependency remains. #115/#117 recovery fixes remain valid for reviews whose selected runtime and formats are supported; their older-image fallback paths require an explicit compatibility audit before this design ships.

## Acceptance criteria for the replacement #102 scope

1. A validated primary registration resolves one project config for primary, linked, and subdirectory invocations; missing/moved/foreign/ambiguous primary state refuses project mutation. Worktree-local config cannot override or deep-merge it.
2. Existing user config and user setup work outside Git; project setup and all project config sections use the primary checkout and preserve owned/foreign boundaries.
3. Each primary or linked worktree may keep its own project-local `node_modules`; AIPR never rewrites, links, deletes, or treats that directory as runtime authority. Consumer CI and runtime builds do not require AIPR installation or a review/doctor gate.
4. The selected global package is identified by its executing module and registered canonical path; cwd, PATH, env, source checkout, local dependency, and API inputs cannot impersonate it. Global in-place upgrades do not require exact project version edits.
5. The current package's packaged, domain-specific compatibility manifest, sealed review provenance, and existing authority checks govern review mutations. Unsupported/unknown old formats and invalid metadata fail before effects; supported formats continue only with existing integrity checks.
6. Older runtime images and worktree-local packages remain evidence or development artifacts and are never executed as an upgrade fallback. Broker, hooks, MCP, and exported writers enforce the same rule, including after async waits.
7. Unsupported review cleanup is bounded to proven current-runtime ownership and protocol; otherwise evidence remains and the operation refuses without guessing or launching older code.
8. Doctor distinguishes registration, config, selected package, integration, format support, identity, and broker health; read-only commands preserve successful output schemas and have no effects.
9. Setup migration is explicit and idempotent, moves `.ai-peer-review.json` to primary `.ai-peer-review/config.json`, centralizes AIPR-neutral setup metadata and skill instructions, changes primary/user integrations once per clone or user, and preserves foreign files and active review evidence. Thin host skill wrappers must demonstrably load the registered primary shared body. A source/local runner cannot bypass global selection.
10. Every tracked AIPR setup output passes the package reference format/lint rules and applicable host file checks before atomic write; setup does not introduce formatter/lint failures, alter the host toolchain, or require manual formatting. The package includes the versioned reference rules and an installed-file check. Host-rule conflicts refuse with specific diagnostics and no partial tracked-file changes.
11. Source-repository CI inspects the exact published tarball and its package manifest: no tests, fixtures, development npm scripts, or source-release/packaging verifier tools ship; the runtime compatibility manifest, deployment verifier, and formatting/lint reference assets do ship. Installed-artifact fixtures cover global upgrade, changed Node/global path, active and terminal older reviews, ordinary/linked/custom Git layouts, paths with spaces, and Windows and POSIX without real global-install or registry mutation. Consumer-project CI fixtures pass without AIPR installed.

## Open implementation sequencing, not design authority

Plan work in independently verifiable slices: primary registration/config; global runner selection and integration migration; review-format support and old-image fence; cross-entry-point enforcement; installed-artifact matrix. The implementation plan must map each criterion to tests and preserve the existing #102 review trail. No implementation begins from the superseded exact-pin plan.
