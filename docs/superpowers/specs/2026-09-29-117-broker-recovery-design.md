# Issue 117: Broker Recovery and Unjoined XPR Retirement

## Status and scope

This design addresses the package defects exposed by the AITM #1841 XPR. Two review workspaces exist with different pinned package images. The older Opus 5 review is unjoined at startup stage `manual`; the newer Opus 5.5 review is unjoined at stage `authority` and has a durable manual fence. Both have Claude session handles and tool-use observations from attempts to run the package-generated `join` command. An AITM Bash hook denied both commands. Neither review has a reviewer participant or reviewer decision event. These are the incident facts recorded in issue #117; they do not prove that no provider request was submitted.

The package must present a usable offline broker recovery route, permit an author to retire a provably unsubmitted review through durable protocol authority, and surface explicit provider errors that explain a failed launch. It must preserve the recorded workspaces and each review's pinned execution image. It will not change AITM hooks or loosen the package-generated absolute `node` and CLI paths. The package will be repacked for local installation; publication to the npm registry is outside this issue. This design does not grant cancellation authority over a provider request that was delivered or whose delivery remains uncertain.

## Recovery authority

`broker status` is a read-only projection. It must enumerate registrations, recovery records, and interrupted startup journals, including `authority` and `manual` stages; an authority-stage crash may precede registration publication. It reports each workspace's review ID, startup stage, runtime digest, and verification result. Authentication requires agreement among canonical project/workspace ownership, sealed protocol startup, request digest, journal, any registration, and the verified runtime image. Malformed, missing, foreign-project, or symlinked evidence remains visible as an unverifiable record with a bounded reason and is never a command candidate. Reading status must not repair reservations, append evidence, initialize provider adapters, or launch a broker/provider.

Candidate ranking is deterministic and advisory. Prefer a candidate with verified evidence of mixed-image recovery support; otherwise use authenticated startup/registration creation time as a recency heuristic, with runtime digest and canonical workspace as stable tie breakers. Missing chronology is reported as unknown, not inferred from a digest, version string, filename, or model name. Equal package versions can have different image contents. Show the complete candidate list, each candidate's ranking reason and quoted reconcile command, and all unverifiable records. Never label an untested candidate compatible or ready. A successful authenticated broker handshake plus reconciliation of all relevant registrations establishes broker recovery readiness; individual reviews may still be recovery-only or blocked on provider evidence.

`broker reconcile <workspace>` remains the mutation that starts that workspace's verified pinned broker image while offline. Validate the chosen image and sealed broker/Node protocol versions immediately before startup and revalidate registrations under broker ownership. A broker using another review's image may construct a recovery-only worker, but it must never dispatch that review under the candidate image. Recovery-only workers must not launch, resume, wake, or acquire provider resources for that review. Do not rewrite registrations or reseal images to make them match.

An old pinned image that cannot construct a recovery-only worker for a newer registration may fail. Preserve its bounded failure evidence and the other candidates; return an actionable next candidate instead of claiming readiness. Do not automatically spawn another broker until authenticated shutdown or OS-enforced ownership proves the failed instance cannot still act. An existing incompatible live broker must be addressed through its authenticated lifecycle, never replaced based on stale files or a failed connection alone. Historical pinned code is immutable; the new package improves selection and recovery around it, rather than claiming the old implementation has acquired new capabilities.

The incident report says that the newer Opus 5.5 image reconciles the older registration as recovery-only. Verify that capability against exact image evidence before recommending it as a known route; otherwise label it the newer candidate awaiting reconciliation. The older Opus 5 review remains recorded and cannot be launched under the newer image.

## Unjoined retirement

### Evidence and eligibility

An author may request `abandon <workspace> --reason <text>` for an awaiting-reviewer review only when the sealed author session matches, the reviewer participant and reviewer claim are absent, no reviewer decision event exists, and durable evidence proves non-submission across every supported dispatch route. Existing intervention-required abandonment retains its separate authority contract; this extension must not route an ineligible unjoined review through intervention to bypass these checks.

Provider non-submission means a launch/wake request was definitely not delivered to the provider. It is distinct from the absence of a protocol `join` or reviewer decision. A Claude session handle, stream/tool observation, hook denial, zero exit, timeout, or generic failure cannot establish provider non-submission. Preserve the original launch classification and observations. In particular, a broker journal with `provider_operation: null` says nothing about a separate `launch-reviewer` invocation.

| Evidence for the exact review and request                                                                                                                                     | Unjoined retirement                                                                        |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Authenticated `authority`, `registered`, or `manual` pre-dispatch journal; all launch routes durably excluded; complete tracked operation history proves no provider dispatch | Eligible after the remaining authority checks                                              |
| Exact launch and wake attempts durably settled as definitely not submitted/refused before delivery, with no contradictory manual launch evidence                              | Eligible after fencing and the remaining checks                                            |
| Claude session/tool-use evidence, acknowledged provider delivery, pending/reserved operation, unknown outcome, or contradictory receipt                                       | Blocked pending exact reconciliation; acknowledged delivery is not a non-submission result |
| Missing/corrupt launch history, unknown legacy manual-launch coverage, unverifiable fence, or unavailable provider evidence                                                   | Blocked; missing evidence is not an empty history                                          |

A `manual` startup only says the broker does not own reviewer dispatch. It is not proof that no manual reviewer was launched. New package-managed manual launches must reserve an exact operation durably before spawning, using the same dispatch exclusion as retirement; completion records must survive crashes. Legacy workspaces without that coverage cannot become eligible merely because a launch-state file is absent. The `authority` extension similarly requires complete pre-dispatch evidence and exclusion, not a stage-name allowlist alone.

### Reconciliation and the #1841 route

Extend `broker reconcile <workspace>` with bounded observation of unresolved manual Claude launch evidence as well as broker/wake operations, including for already fenced recovery-only workspaces. This observation must not launch or resume Claude, submit an invitation, register a reviewer, or clear a fence. Bind any resulting receipt to the review ID, request digest, operation/intent identity, pinned runtime digest, observed session fingerprint when present, source/version, and source evidence digest. Recheck those bindings before consuming it. A verified final provider receipt saying the exact operation was rejected before delivery can establish non-submission only if every relevant attempt is covered and no session/tool-use evidence contradicts it. An unbound user assertion or pasted provider error is insufficient.

The result must distinguish `definitely-not-submitted`, `submitted`, and `outcome-unknown`, and preserve the source evidence and prior attempt history. A completed session transcript can confirm provider activity; it cannot retroactively make an executed launch unsubmitted. Missing provider support, incomplete history, active sessions, timeouts, and unresolved legacy operation identity return `outcome-unknown` with the exact blocking evidence. No repeated reconciliation loop may silently retry a launch. The current adapter does not supply a general proof for legacy manual launches; implementation must expose this unsupported outcome truthfully and test it.

Consequently, the currently recorded #1841 hook denials and absent joins are insufficient to retire either observed Claude launch through this non-submission path. They stay preserved and blocked unless stronger exact evidence satisfies the contract. This limitation must be explicit in CLI guidance and implementation acceptance evidence.

A fresh review remains possible without deleting or falsifying those attempts: use normal `start` with a fresh, collision-free output scope, such as a distinct `--reviews-root` or `--review-path-template`, which participates in deterministic review identity. Verify that the resulting review ID, invitation, and all output paths differ before any dispatch. Changing `--record-id` alone does not guarantee a new review ID. Retain the old reservations, registrations, launch evidence, and blocked status; do not present the new review as a supersession or as resolution of the older provider uncertainty. A consumer requiring retirement or consolidated lineage must remain blocked under its own rules. Reusing an old reserved scope requires qualifying terminalization; cancellation after actual provider delivery would require a separately specified authority contract.

### Mutation and race safety

Use the established lock order: dispatch exclusion first, then the review mutation lock. Before terminalization, broker-owned startup requires a durable suspension/fence and authenticated worker settlement or OS-enforced offline broker ownership. A fence excludes future automatic dispatch but does not prove any previous launch outcome. Do not invoke a reconciliation callback capable of provider dispatch while holding retirement authority.

Within dispatch exclusion, inspect complete broker, manual-launch, and wake histories and freeze their exact operation identities and evidence digests. Under the review mutation lock, re-read protocol authority and all relevant evidence, validate the same sealed author and expected review ID, revision, sequence, and actor, and append the terminal event only if all predicates still hold. Compare full operation identity/status and proof evidence, not just startup stage or the latest wake status. Any changed evidence fails closed. All package-managed launch/resume/wake entry points must honor the same exclusion and recheck terminal/fence state before provider effects; a newly started manual process cannot slip between eligibility checking and abandonment.

If a reviewer joins first, the expected authority becomes stale and abandonment fails without releasing its reservation. If abandonment wins, late `join` and `submit` fail under protocol authority. A process already dispatched before fencing remains an unresolved operation and prevents this retirement path. Pinned legacy callers must not be assumed to honor a new fence or launch ledger; absent verified compatible exclusion/settlement, their workspace remains blocked.

Release the collateral reservation only after the terminal event is durable, while preserving lock ordering and verifying its exact review/request/path ownership and regular-file identity. Never remove a foreign, replaced, malformed, or symlinked reservation. A crash after the event but before cleanup leaves a terminal review with cleanup pending: an exact retry by the same actor/reason must finish owned cleanup without appending another terminal event. Conflicting retries fail. Exact `start` retries of an abandoned review remain terminal, do not contact providers, and do not recreate a reservation. Keep all other launch state, observations, and broker records on disk.

## Claude launch diagnostics

An explicit structured Claude error that states the installed Claude Code version is below a required version should produce a bounded diagnostic with the observed and required versions and an update instruction. Before implementation, capture a sanitized fixture from the actual supported provider envelope and document the exact allowlisted code/fields (or narrowly specified structured-message pattern); do not invent an assumed provider error shape or search arbitrary stderr for version-like text. Accept only bounded valid version strings and a meaningful observed-below-required comparison. Malformed, contradictory, oversized, or unsupported envelopes retain the existing generic classification.

Extend the diagnostic schema, normalizer, result validation, CLI rendering, and tests together. Retain the existing 256-byte message/action and 1024-byte total diagnostic bounds. Never echo arbitrary provider text, prompts, paths, or raw stderr. An error that lacks an observed version must not use a guessed locally installed version as though the provider observed it.

A documented model or effort rejection remains `APR_REVIEWER_SELECTION_REFUSED` only when the provider explicitly identifies that selection and existing absence-of-session/unchanged-authority guards hold. Preserve precedence for an authenticated reviewer decision even if process exit or provider diagnostics indicate a failure. A generic nonzero exit, absent JSON, tool hook denial, or missing reviewer event remains a failed or uncertain launch according to current classification and requires status/reconciliation. `failed` is not durable non-submission proof. Updating Claude must be followed by status and reconciliation before any retry; version diagnostics must not authorize rerunning an uncertain launch. No diagnostic constitutes protocol submission or retirement authority.

## CLI and agent guidance

`help broker`, `help abandon`, and `explain` must distinguish offline status from the reconciliation command that starts a pinned broker. Status output shows the full candidate list; help explains ranking, recovery-only workers, retained evidence, and failed-candidate ownership checks. Refused retirement reports the precise missing authority/proof, the quoted reconciliation command where supported, and an explicit unsupported/unknown result where it cannot be resolved automatically. Include the independent fresh-output route and its retained-ambiguity limitation.

Add the missing `APR_LINEAGE_UNAVAILABLE` explanation. `supersede` still requires valid lineage and cannot replace abandonment when no lineage receipt exists. Help must avoid saying that an unjoined review was never launched merely because the broker journal lacks a provider operation.

## Verification

Use disposable synthetic workspaces and pinned fixtures; do not mutate or launch the preserved #1841 attempts. New tests must fail against the current implementation before the repair. The implementation plan must cover these observable outcomes:

1. Mixed-image offline status selects the newer recovery candidate even when both package versions match and lexical ordering prefers the old workspace. Cover timestamps/ties, authority journals without registrations, unverifiable evidence, and zero status writes/provider calls. Reproduce old-image refusal, failed-instance ownership protection, and successful newer-image recovery-only reconciliation with zero dispatch/resource acquisition for the old review. Assert pinned images and registration bytes are unchanged.
2. Eligible unsubmitted `manual`, `authority`, and `registered` attempts reach a terminal state only under exact author and proof authority. Manual sessions/tool observations remain blocked even when the broker operation is null. Missing or corrupt legacy evidence, foreign proof, stale receipts, acknowledged launch/wake, and earlier unresolved operations followed by a settled latest operation remain blocked. Reconciliation makes no provider dispatch and preserves evidence/fences on unavailable observation and timeout.
3. Deterministic barriers exercise both join/abandon orderings, manual launch/abandon, wake/fence, and evidence replacement races. Assert one valid outcome, no provider effects after terminalization, no release on refusal, and rejection of late join/submit. Test crash after durable event before reservation release, exact and conflicting retry, foreign/symlink reservation refusal, and terminal exact `start` without broker startup or reservation recreation.
4. The fresh-output route creates a different review ID and invitation while leaving ambiguous old reviews and reservations intact. Changing only record ID must not be advertised as sufficient. Output collision and lineage checks remain enforced.
5. Diagnostic fixtures cover the actual structured version-floor error, malformed/oversized/injected/contradictory version data, generic nonzero exit, missing JSON, hook denial, explicit selection refusal with and without a session, and a valid reviewer decision accompanied by a nonzero exit. Verify schema/rendering bounds and no new retry or non-submission authority.

Run all issue #117 verification commands during implementation delivery: the broker upgrade/startup tests; broker release/supersession-lineage tests; Claude classifier/bootstrap tests; help/CLI-parse tests; `npm test`; `npm run test:packaging`; `npm run test:slow`; lint; format; and commit inspection. These are implementation gates, not claims that a specification review implements the behavior. Before any authorized global reinstall, validate the local tarball's packaged content, successful installation in a disposable location, and SHA-256. Do not publish it.
